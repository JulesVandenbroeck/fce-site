FCE-site design explorations

Three ways to build the analysis graph

Three complete, standalone renderings of the same mission screen (M-1 · First Light), each answering the node-graph question (docs/design-brief.md §4) a different way: what a graph remembers about where a node sits, and what gesture joins two of them. This page is the M1 checkpoint — open each page, then read README.md for the recommendation.

Style A

Beamline →

Persists: an ordered edge list, and nothing else. The graph container carries one attribute holding the sequence of source→destination node-id pairs a student has connected. No node carries a position, so there is nothing to remember about where anything sits on screen — layout is a straight rail, recomputed by ordinary flex flow every time.

Connects by: clicking. Click an output port to arm it, then click an input port on a different node to complete the connection. Dragging a port does nothing on purpose.

Gives up: any spatial arrangement at all — a student cannot place two related nodes near each other. In exchange, it is the only one of the three with a real answer at 768 px: the rail simply wraps, rather than needing a scrolling canvas.

Style B

Bench →

Persists: a free position per node — {id, x, y} — plus the edge list. A student can drag any node anywhere on an open canvas and that placement survives a reload, so grouping related nodes or spreading a wide pipeline out is a real tool, not an accident of add order.

Connects by: dragging. Press an output port, drag to an input port on another node, and release to link them. A plain press-and-release in place on a port is deliberately inert — it is dragging or nothing.

Gives up: a graph reading the same way twice. Two students who build an identical pipeline can leave it looking entirely different, and the canvas needs real width to be worth having — it is the one style with no strong story at 768 px.

Style C

Board →

Persists: a node's pipeline stage and its position within that stage — column and slotIndex — plus the edge list. A node's column is fixed by its kind (Data always lane 0, Histogram always lane 4); slotIndex is its order within that lane's own list, read back from live DOM order rather than tracked separately. The result figure lives inside the graph itself, as the Histogram lane's own content.

Connects by: either drag or click — both gestures work here. Drag from an output port to an input port, or click one and then the other, and either completes the connection.

Gives up: Bench's free arrangement (a node cannot sit next to an unrelated one just because a student wants them near each other) and Beamline's single-glance simplicity — five typed lanes read as more machinery than one rail, and the whole board needs to scroll horizontally once those five lanes exceed 768 px.

Nothing on this page, or on the three it links, ships in the application. Each is a complete standalone render — open any of the three directly as a file:// URL, with no server and no build step — built to be compared here, not to be the final markup. The recommendation and what each option gives up in full are in README.md.
